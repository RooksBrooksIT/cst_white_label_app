1. EXECUTIVE FINANCIAL ARCHITECTURAL SUMMARY
================================================================================
The CST White Label Application (eBricks Construction ERP) implements an enterprise-
grade, dual-entry synchronized financial system. Construction projects inherently
involve distributed spending across dispersed physical sites with asynchronous
approvals, fluctuating material costs, contractor milestone advances, and localized
petty cash expenditures.

Key Capabilities of the Financial Engine:
- Multi-Tier Inflow / Outflow Separation: Clear segregation between Project Owner
  Receipts, Org-Level Capital Outlays, Site-Level Manager Procurements, and Daily
  Supervisor Field Expenses.
- 5-Category Expense Taxonomy: Automated categorization into (1) Supervisor Field
  Expenses, (2) Manager Expenses, (3) Organization Corporate Expenses, (4) Contractor
  Contract Expenses, and (5) Worker/Supervisor Performance Incentives.
- Real-Time Atomic Transaction Sync (ExpenseService): Zero race-condition summation
  that recalculates all category totals and synchronously updates project balance
  sheets across `projects`, `Site`, and `totalSiteExpensesPerDay` collections.
- Isolated Petty Cash Micro-Accounting: Dedicated account ledgers with dynamic
  balance tracking, automated 10% low-balance warning triggers, and cycle archiving.
- Multi-Role Financial Access Control: Organization Admins maintain macro financial
  visibility; Managers monitor site budgets; Supervisors record micro field expenses;
  and Customers view certified stage completion statements without seeing internal
  vendor cost margins.
- Tamper-Evident Multi-Tenant Isolation: Financial documents are strictly sandboxed
  under `/organisation/{orgId}/data/...` with Firestore security rules preventing
  cross-tenant data leakage.

2. COMPREHENSIVE CASH FLOW MODEL (INFLOW VS. OUTFLOW TAXONOMY)
================================================================================

+-----------------------------------------------------------------------------------+
|                        PROJECT FINANCIAL ARCHITECTURE                             |
+-----------------------------------------------------------------------------------+
|                                                                                   |
|  [ INFLOWS / CAPITAL INTAKE ]                      [ OUTFLOWS / SITE EXPENSES ]   |
|  1. Project Total Budget (Estimated Cost)          1. Supervisor Field Purchases  |
|  2. Client Milestone Payments (amountPaid)         2. Manager Procurements        |
|  3. Petty Cash Allocation Advances                 3. Org Direct Overhead/Bills   |
|  4. SaaS Organization Subscriptions (PayU)         4. Contractor Contract Claims  |
|                                                    5. Productivity Incentives     |
|                                                                                   |
|                               +------------------+                                |
|                               |  ExpenseService  |                                |
|                               |  Atomic Engine   |                                |
|                               +--------+---------+                                |
|                                        |                                          |
|                                        v                                          |
|                       +----------------------------------+                        |
|                       |   amountSpent = Sum(Categories)  |                        |
|                       |   amountBalance = Paid - Spent   |                        |
|                       +----------------------------------+                        |
+-----------------------------------------------------------------------------------+

2.1 INFLOWS (Capital Intake & Revenue Streams)
---------------------------------------------
1. Project Estimated Budget (`totalCost` / `projectCost` / `budget`):
   - Defined during Site & Project Onboarding in `projects` and `Site` collections.
   - Represents the total contract value agreed with the project owner.

2. Client Milestone Receipts (`amountPaid` / `amountReceived` / `paid`):
   - Injected into the project account when the client/customer makes a stage-based
     progress payment (e.g., Foundation, Plinth, First Floor Slab, Finishing).
   - Stored on both the `projects` and `Site` documents.

3. Supervisor Petty Cash Advances (`totalAllocated` / `currentCycleAllocated`):
   - Capital dispatched by Organization HQ or Project Managers into a site
     supervisor's petty cash float account (`petty_cash_accounts`).

4. SaaS Subscription Revenue (PayU Gateway):
   - Recurring organization subscription revenue (Silver, Gold, Platinum, Enterprise)
     processed via PayU S2S payment gateway, generating instant tax invoices.

2.2 OUTFLOWS (The 5 Expense Categories + Petty Cash Disbursements)
-----------------------------------------------------------------
Every expenditure incurred across physical construction sites is routed into one of
the 5 core expense categories managed by `ExpenseService`:

Category 1: `siteSupervisorEntries` -> Micro on-site operational field costs.
Category 2: `managerEntries` & `managerExpenseSummary` -> Manager procurement orders.
Category 3: `organizationEntries` & `organizationExpenseSummary` -> Bulk HQ invoices.
Category 4: `contractorEntries` -> Sub-contractor milestone payouts.
Category 5: `siteSupervisorIncentives` -> Performance and productivity bonuses.

4. ATOMIC RECONCILIATION & SYNC ENGINE (ExpenseService.dart)
================================================================================
Located at: `lib/services/expense_service.dart`

4.1 Multi-Collection Aggregation Algorithm
------------------------------------------
Whenever an expense is created, edited, or deleted anywhere in the application,
`ExpenseService.recalcTotalsAndSyncProject(siteId)` is triggered. It gathers and sums
all 5 categories in parallel:

```dart
final supervisorTotal   = await _sumSupervisorExpenses(siteId);
final managerTotal      = await _sumManagerExpenses(siteId);
final organizationTotal = await _sumOrganizationExpenses(siteId);
final contractorTotal   = await _sumContractorExpenses(siteId);
final incentiveTotal    = await _sumIncentiveExpenses(siteId);

final double totalAllExpenses = supervisorTotal +
    managerTotal +
    organizationTotal +
    contractorTotal +
    incentiveTotal;
```

4.2 Firestore Atomic Transaction Blueprint
------------------------------------------
To guarantee mathematical consistency without dirty reads or concurrent overwrite
issues, `ExpenseService` executes an atomic Firestore transaction (`runTransaction`):

```dart
await firestore.runTransaction((txn) async {
  final totalsRef = FirestoreService.getCollection('totalSiteExpensesPerDay').doc(siteId);
  final projectRef = await _findExistingProjectDocBySiteId(siteId);
  final siteRef = await _findExistingSiteDocBySiteId(siteId);

  // 1. Transactional Reads
  DocumentSnapshot<Map<String, dynamic>>? projectSnap;
  if (projectRef != null) projectSnap = await txn.get(projectRef);

  DocumentSnapshot<Map<String, dynamic>>? siteSnap;
  if (siteRef != null) siteSnap = await txn.get(siteRef);

  // 2. Upsert Category Totals Document
  txn.set(
    totalsRef,
    {
      'siteId': siteId,
      'totalSiteExpense': supervisorTotal,
      'totalMgrExpense': managerTotal,
      'totalOrgExpense': organizationTotal,
      'totalContractorExpense': contractorTotal,
      'totalIncentiveExpenses': incentiveTotal,
      'totalAllExpenses': totalAllExpenses,
      'updatedAt': FieldValue.serverTimestamp(),
    },
    SetOptions(merge: true),
  );

  // 3. Compute Project Balance & Update Project Document
  if (projectRef != null && projectSnap != null && projectSnap.exists) {
    final data = projectSnap.data();
    double amountPaid = (data?['amountPaid'] ?? data?['paid'] ?? data?['amountReceived'] ?? 0.0).toDouble();
    final amountBalance = amountPaid - totalAllExpenses;

    txn.update(projectRef, {
      'amountSpent': totalAllExpenses,
      'amountSpend': totalAllExpenses,
      'amountBalance': amountBalance,
      'updatedAt': FieldValue.serverTimestamp(),
    });
  }

  // 4. Update Site Collection Document
  if (siteRef != null && siteSnap != null && siteSnap.exists) {
    final sData = siteSnap.data();
    double sAmountPaid = (sData?['amountPaid'] ?? sData?['paid'] ?? sData?['amountReceived'] ?? 0.0).toDouble();
    final sAmountBalance = sAmountPaid - totalAllExpenses;

    txn.update(siteRef, {
      'amountSpent': totalAllExpenses,
      'amountSpend': totalAllExpenses,
      'amountBalance': sAmountBalance,
      'updatedAt': FieldValue.serverTimestamp(),
    });
  }
});
```

4.3 Dynamic Balance Formula
---------------------------
At any point in time, the net site financial health is expressed as:
```
+-------------------------------------------------------------+
| Net Balance = Total Client Inflow - Total Category Outflow  |
|                                                             |
| amountBalance = amountPaid - (                              |
|     totalSiteExpense        (Supervisor)                    |
|   + totalMgrExpense         (Manager)                       |
|   + totalOrgExpense         (Organization HQ)               |
|   + totalContractorExpense  (Contractors)                   |
|   + totalIncentiveExpenses  (Incentives)                    |
| )                                                           |
+-------------------------------------------------------------+
```
- If `amountBalance > 0`: Site is operating with positive cash liquidity.
- If `amountBalance < 0`: Site is in a cash deficit (expenditures have outpaced
  client milestone receipts, alerting Organization HQ to request stage payment).

4.4 Automatic Background Trigger Hooks Across the Application
-------------------------------------------------------------
`ExpenseService.recalcTotalsAndSyncProject(siteId)` is automatically invoked across:
1. `site_entry_page.dart` -> When supervisor adds/updates field expense.
2. `manager_expenses.dart` & `manager_site_entry_page.dart` -> On manager entries.
3. `organization_expenses.dart` -> On corporate HQ direct expense logging.

5. `incentive_calculation_sheet.dart` -> On supervisor/worker bonus submission.
6. `site_financial_details_page.dart` -> Lazy sync check upon viewing dashboard.

5. SUPERVISOR PETTY CASH ACCOUNT & CYCLE LIFECYCLE (PettyCashService.dart)

Located at: `lib/services/petty_cash_service.dart` & `lib/models/petty_cash_models.dart`

5.1 Dual-Tier Model: Account Ledger vs. Transaction Journal
-----------------------------------------------------------
The petty cash module operates as an isolated sub-ledger with strict balance checks:
- Account Document: `/organisation/{orgId}/data/petty_cash_accounts/{supervisorId}`
- Transaction Subcollection: `.../petty_cash_accounts/{supervisorId}/transactions/{txnId}`
- Archival Cycle Subcollection: `.../petty_cash_accounts/{supervisorId}/cycles/{cycleId}`

```
+-----------------------------------------------------------------------+
|                SUPERVISOR PETTY CASH DATA STRUCTURE                   |
+-----------------------------------------------------------------------+
|  petty_cash_accounts/{supervisorId}                                  |
|   ├── totalAllocated: double          (All-time capital allocated)    |
|   ├── totalUsed: double               (All-time capital spent)        |
|   ├── availableBalance: double        (Current spendable balance)     |
|   ├── currentCycleAllocated: double   (Current cycle float)           |
|   ├── lowBalanceThresholdPercent: 10% (Alert trigger point)           |
|   ├── lowBalanceTriggered: bool       (Warning status)                |
|   │                                                                   |
|   ├── transactions/{txnId}            (Itemized disbursements)        |
|   │    ├── amount, category, purpose, receiptUrl, isApproved, siteId |
|   │                                                                   |
|   └── cycles/{cycleId}                (Closed monthly/milestone logs) |
|        ├── cycleAllocated, cycleUsed, openingBalance, closingBalance  |
+-----------------------------------------------------------------------+
```

5.2 Cycle Allocation & Advance Top-Up Pipeline
----------------------------------------------
When an Organization Admin or Manager allocates funds to a Supervisor:
1. Manager enters amount and selects Supervisor in `manager_petty_cash_page.dart`.
2. `PettyCashService.allocatePettyCash(...)` executes:
   - Increments `totalAllocated += amount`
   - Increments `availableBalance += amount`
   - Increments `currentCycleAllocated += amount`
   - Resets `lowBalanceTriggered = false`
   - Logs an allocation transaction of type `credit`.
   - Sends real-time FCM notification to Supervisor.

5.3 Transaction Capture, Receipt Upload & Balance Subtraction
-------------------------------------------------------------
When a Supervisor spends money on-site:
1. Supervisor opens `supervisor_petty_cash_page.dart`, snaps receipt image, selects
   expense category (Fuel, Food, Hardware, Labour Advance, Transport), and enters amount.
2. `PettyCashService.recordExpense(...)` executes inside a Firestore transaction:
   - Validates that `amount <= availableBalance` (prevents overspending).
   - Decrements `availableBalance -= amount`.
   - Increments `totalUsed += amount`.
   - Uploads receipt image to Firebase Storage.
   - Evaluates whether new `availableBalance <= (currentCycleAllocated * 10%)`.
   - If low: sets `lowBalanceTriggered = true` and dispatches high-priority push.

5.4 Automated 10% Low-Balance Warning System
--------------------------------------------
```dart
double get lowBalanceThresholdAmount =>
    (currentCycleAllocated > 0 ? currentCycleAllocated : totalAllocated) *
    (lowBalanceThresholdPercent / 100.0);

bool get isLowBalance =>
    totalAllocated > 0 && availableBalance <= lowBalanceThresholdAmount;
```
When `isLowBalance == true`:
- The Supervisor UI displays a dynamic amber/red warning banner.
- High-priority FCM push notification is dispatched to the assigned Manager:
  "Alert: Supervisor [Name]'s petty cash balance has dropped below 10% (₹[Balance] remaining). Please review and top up."

5.5 Cycle Closure & PDF Cashbook Statement Generation
-----------------------------------------------------
- Cycles can be closed at end-of-month or project milestones via `closePettyCashCycle(...)`.
- The cycle is archived in the `cycles` subcollection with opening balance, all
  transactions, total spent, and closing balance.
- `petty_cash_report_pdf_helper.dart` exports a print-ready PDF statement featuring
  the organization logo, itemized table of expenses, embedded receipt thumbnails,
  and supervisor/manager digital signature blocks.

6. 5-STAGE REQUISITION APPROVAL TO EXPENSE SETTLEMENT PIPELINE
================================================================================
Located at: `lib/services/approval_workflow_service.dart`

High-value site expenses (bulk material purchases, machinery hiring, large contractor
advances) undergo a formal 5-stage approval lifecycle before being converted into
settled expense entries:

```
+-----------------------------------------------------------------------------------+
|                     5-STAGE REQUISITION APPROVAL PIPELINE                         |
+-------------------+-------------------+--------------------+----------------------+
| STAGE 1           | STAGE 2           | STAGE 3            | STAGE 4 & 5          |
| Supervisor        | Manager           | Organization HQ    | Manager Release &    |
| Requisition       | Verification      | Authorization      | Site Confirmation    |
+-------------------+-------------------+--------------------+----------------------+
| Supervisor logs   | Manager checks    | Org Admin reviews  | Manager releases     |
| request with item | rates, vendor     | corporate budget   | funds/PO. Supervisor |
| specs & estimate. | quotes & urgency. | & authorizes pay.  | confirms receipt.    |
| Status:           | Status:           | Status:            | Status:              |
| pending_manager_  | pending_org_      | pending_manager_   | approved / received  |
| review            | approval          | clearance          | (Expense Settled)    |
+-------------------+-------------------+--------------------+----------------------+
```

Requisition Settlement Flow:
1. Requisition is submitted via `material_request_form.dart` or `org_site_payment_screen.dart`.
2. Upon passing Stage 3 (Org HQ Authorization) and Stage 4 (Manager Clearance),
   the requisition is marked `approved` or `received`.
3. The cleared financial amount is automatically written to the corresponding
   expense collection (`managerEntries` or `organizationEntries`).
4. `ExpenseService.recalcTotalsAndSyncProject(siteId)` is triggered to immediately
   reflect the approved expenditure in the project's financial balance sheet.

10. PRODUCTION BEST PRACTICES, AUDIT TRAILS & INTEGRITY SAFEGUARDS
================================================================================
1. Zero Dirty Reads (Transactions):
   All expense aggregation and balance recalculation in `ExpenseService` runs inside
   `firestore.runTransaction()`. This completely prevents race conditions when
   multiple supervisors and managers record expenses simultaneously.

2. Multi-Tenant Namespace Partitioning:
   All financial paths are strictly namespaced under `/organisation/{orgId}/data/...`.
   Every document contains `app_id: 'cst_white_label'`, preventing data crossover in
   shared Firebase environments.

3. Complete Receipt Backing:
   Disbursements in petty cash and supervisor entries require receipt image capture
   stored in Firebase Storage with secure direct links embedded in the document.

4. Dual-Key Project Synchronization:
   `ExpenseService` automatically synchronizes both `projects` and `Site` collections
   to ensure backward compatibility across all existing screens.

5. Safe Number Parsing:
   All financial UI components utilize `_parseNum(...)` and `_formatCurrency(...)`
   to safely handle nulls, strings with currency symbols (₹, ,), and double precision
   without throwing unhandled runtime exceptions.
