1. EXECUTIVE ARCHITECTURAL SUMMARY
================================================================================
The notification system in the CST White Label Application (eBricks Construction
ERP) is a robust, production-grade dual-engine framework designed to handle both
instant real-time event alerts and recurring cron-based background deliveries.

The system connects three principal stakeholder roles:
1. Supervisor: Site execution, daily logs, material/tool/payment requisitions,
   petty cash management.
2. Manager: Project oversight, site configuration, stage-1 verification,
   fund dispatch, clearance.
3. Organization Admin / HQ: Corporate financial control, budget authorization,
   subscription management, enterprise-wide compliance.

Key Architectural Capabilities:
- Full Multi-Tenant Isolation: Every token, notification, and schedule is partitioned
  by `orgId` and `app_id`.
- Dual-Write Persistence: Written both globally (`/notifications`, `/fcmTokens`)
  and in organization-scoped subcollections (`/organisation/{orgId}/notifications`,
  `/organisation/{orgId}/fcmTokens`) to allow localized querying and high-throughput
  global Cloud Function triggers.
- Multi-Level Push Delivery: Cloud Firestore `onCreate` triggers -> Firebase Admin SDK
  Multicast Push -> Device heads-up alerts with deep-navigation payloads.
- Automated Scheduled Engine: Serverless Cron executing every 5 minutes with atomic
  transaction locking to guarantee zero duplicate pushes.
- Automatic Stale Token Self-Healing: Instant pruning of unregistered or invalid FCM tokens.
- Rich In-App UX: Custom floating SnackBars for foreground arrivals and click-to-action deep
  linking directly into relevant approval screens via `NotificationRouter`.

3. CLIENT-SIDE LIFECYCLE & FLUTTER INTEGRATION
================================================================================

3.1 Initialization, Background Handler & Cold-Start Recovery
-------------------------------------------------------------
- Entry Point: `NotificationService.initialize(GlobalKey<NavigatorState> navigatorKey)`
  invoked in `lib/main.dart` before `runApp`.
- Top-Level Background Handler: Annotated with `@pragma('vm:entry-point')`,
  `firebaseMessagingBackgroundHandler(RemoteMessage message)` ensures that terminated
  or background state messages are captured without throwing VM isolates errors.
- Cold-Start Launching: When the app is launched directly from a killed state by tapping
  a system tray notification, `_messaging.getInitialMessage()` retrieves the payload.
  A post-frame callback `WidgetsBinding.instance.addPostFrameCallback` ensures the
  navigator context is mounted before calling `navigateToTarget(context, payload)`.

3.2 Local Notification Channel & Android 13+ Runtime Permissions
-----------------------------------------------------------------
- Uses `flutter_local_notifications` plugin for Android 8.0+ Oreo and Android 13+ Tiramisu.
- Android Notification Channel:
  * Channel ID: `cst_high_importance_channel`
  * Channel Name: `High Importance Notifications`
  * Importance: `Importance.max`
  * Priority: `Priority.high`
  * Sound: `default`
  * Vibration & Lights: Enabled
- Explicitly requests `POST_NOTIFICATIONS` runtime permission on Android 13+ devices
  via `AndroidFlutterLocalNotificationsPlugin.requestNotificationsPermission()`.

3.3 Foreground In-App Banners & SnackBar Alerts
------------------------------------------------
- When a push arrives while the user is actively using the app, `FirebaseMessaging.onMessage`
  intercepts the event.
- Displays a custom dark floating banner (`Color(0xFF0F172A)`) with rounded corners (16px),
  vibrant notification icon, bold title, two-line body truncation, and a tap chevron.
- Tapping the banner immediately dismisses the SnackBar and navigates to the target page.

3.4 Device FCM Token Lifecycle & Dual-Write Storage
----------------------------------------------------
- Method: `NotificationService.saveToken({userId, userType, userName})`
- Triggered upon login across all application screens:
  * Supervisor: `supervisor_login_page.dart` & `landing_page.dart`
  * Manager: `config_login.dart` & `landing_page.dart`
  * Organization HQ: `organisation_login_page.dart` & `landing_page.dart`
  * Session Loading: `portal_loading_screen.dart`
- Dual-Write Pattern:
  1. `/organisation/{orgId}/fcmTokens/{userId}`: Scoped specifically to tenant organization.
  2. `/fcmTokens/{orgId}_{userId}`: Global root collection for cross-organization lookups
     and high-speed Cloud Functions execution.
- Token Refresh: `_messaging.onTokenRefresh.listen` handles automatic token updates
  whenever Google Play Services or APNs issues a new registration token.

4. THE 5-STAGE REQUISITION APPROVAL WORKFLOW NOTIFICATION MATRIX
===============================================================================
Implemented in `lib/services/approval_workflow_service.dart`:

4.1 Stage 1: Requisition Submission (Supervisor -> Manager)
-------------------------------------------------------------
- Triggered by: Supervisor submitting Material Request, Tools Request, or Site Payment.
- Helper Invoked: `NotificationService.notifyManager(...)`
- Notification Content:
  * Title: "📦 New Material Requisition", "🔧 New Tools Requisition", or "💳 New Payment Request"
  * Body: "Supervisor [Name] submitted [ReqId] for Site [SiteId] - [SiteName]."
- Target Role: `manager`
- Push Destination: All managers & config users registered under the site's `orgId`.
- Recipient Action: Tap opens corresponding Manager Approval Screen.

4.2 Stage 2: Manager Verification & Forwarding (Manager -> Org HQ)
-------------------------------------------------------------------
- Triggered by: Manager verifying Stage 1 requisition and forwarding to Organization HQ.
- Helper Invoked: `NotificationService.notifyOrganisation(...)`
- Notification Content:
  * Title: "🏢 Requisition Verified & Awaiting HQ Authorization"
  * Body: "Manager [Name] verified [ReqId] for Site [SiteId]. Awaiting Organization authorization."
- Target Role: `organisation`
- Push Destination: Organization HQ Administrators.
- Status Update: `manager_approved` / `pending_org_approval`.

4.3 Stage 2 (Reject): Manager Rejection (Manager -> Supervisor)
----------------------------------------------------------------
- Triggered by: Manager rejecting requisition at Stage 1.
- Helper Invoked: `NotificationService.notifySupervisor(...)`
- Notification Content:
  * Title: "❌ Requisition Declined by Manager"
  * Body: "Your requisition [ReqId] for Site [SiteId] was rejected by Manager [Name]. Reason: [Remarks]"
- Target Role: `supervisor`
- Target Supervisor: `forSupervisorName: [SupervisorName]`
- Status Update: `rejected_by_manager`.

4.4 Stage 3: Organization HQ Authorization (Org HQ -> Manager)
---------------------------------------------------------------
- Triggered by: Organization HQ approving the requisition.
- Helper Invoked: `NotificationService.notifyManager(...)`
- Notification Content:
  * Title: "✅ Requisition Authorized by HQ"
  * Body: "Organization HQ has authorized [ReqId] for Site [SiteId]. Please proceed with clearance."
- Target Role: `manager`
- Status Update: `org_approved` / `pending_manager_clearance`.

4.5 Stage 3 (Reject): Organization HQ Rejection (Org HQ -> Supervisor & Manager)
--------------------------------------------------------------------------------
- Triggered by: Organization HQ declining the requisition.
- Helper Invoked: Dual notification:
  1. `NotificationService.notifySupervisor(...)`
  2. `NotificationService.notifyManager(...)`
- Notification Content:
  * Title: "❌ Requisition Declined by Organization HQ"
  * Body: "Requisition [ReqId] was declined by Organization HQ. Reason: [Remarks]"
- Status Update: `rejected_by_org`.

4.6 Stage 4: Manager Release & Fund Dispatch (Manager -> Supervisor)
---------------------------------------------------------------------
- Triggered by: Manager completing final verification and releasing goods/funds.
- Helper Invoked: `NotificationService.notifySupervisor(...)`
- Notification Content:
  * Title: "🚀 Requisition Approved & Dispatched"
  * Body: "Your requisition [ReqId] has been fully approved and released by Manager [Name]."
- Target Role: `supervisor`
- Target Supervisor: Specific requesting supervisor.
- Status Update: `completed` / `released`.

4.7 Stage 5: Site Completion & Material Receipt Audit
------------------------------------------------------
- Triggered by: Supervisor confirming physical receipt of materials or tools at site.
- In-App audit entry updated for Manager and Organization audit screens.

5.1 Petty Cash Workflow & 10% Low-Balance Alert Engine
-------------------------------------------------------
File: `lib/services/petty_cash_service.dart`
Petty cash operations trigger automated multi-tier notifications:
1. Petty Cash Request Submission:
   - Supervisor requests funds -> Notifies Manager & Org HQ (`NotificationService.notifyManagerAndOrganisation`).
   - Title: "💰 New Petty Cash Request: ₹[Amount]"
   - Body: "Supervisor [Name] submitted request [ReqId] for Site [SiteName]."
2. Petty Cash Manager Verification:
   - Manager forwards request -> Notifies Org HQ (`NotificationService.notifyOrganisation`).
3. Organization Top-up Approval & Fund Dispatch:
   - Org authorizes -> Notifies Supervisor & Manager (`NotificationService.notifySupervisor`).
   - Title: "💵 Petty Cash Dispatched: ₹[Amount]"
   - Body: "Top-up of ₹[Amount] credited to Site [SiteName] petty cash wallet."
4. 10% Low-Balance Threshold Alert:
   - When supervisor logs an expense and remaining wallet balance drops below 10% of total
     allocated budget (`currentBalance <= 0.10 * totalBudget`):
   - Automatically triggers high-priority alert to Supervisor and Manager.
   - Title: "⚠️ Low Petty Cash Balance Alert"
   - Body: "Site [SiteName] petty cash balance is ₹[Balance] (< 10% of allocated budget). Please initiate top-up."

5.3 Material Inventory Low-Stock & Site Transfer Alerts

7.1 Client-Side Scheduling Interface & Helpers
-----------------------------------------------
Located in `lib/services/notification_service.dart`:

7.3 Firebase Cloud Functions Pub/Sub Cron Worker (processScheduledNotifications)
---------------------------------------------------------------------------------
- File: `functions/index.js`
- Trigger: `functions.pubsub.schedule("every 5 minutes").timeZone("Asia/Kolkata")`
- Operation:
  1. Scans `/scheduled_notifications` where `status == 'pending'` and `scheduledAt <= now`.
  2. Batch limit: 50 documents per run.

7.4 Concurrency Control, Atomic Locks & Duplicate Prevention
-------------------------------------------------------------
- Worker uses Firestore `db.runTransaction` to atomically transition `status: 'pending'`
  to `status: 'processing'`.
- If two cron instances run concurrently, only one successfully claims the document.
- Once processed, dispatches FCM Multicast Push and creates an in-app notification record.

7.5 Recurrence Rescheduling Algorithm (Daily / Weekly)
-------------------------------------------------------
- If `repeat === 'daily'`:
  Adds 24 hours to `scheduledAt`. If next date is still in past, advances to tomorrow.
  Updates document with `status: 'pending'`, new `scheduledAt`, and increments `deliveredCount`.
- If `repeat === 'weekly'`:
  Adds 7 days to `scheduledAt`, updates `status: 'pending'`.
- If `repeat === 'none'`:
  Marks `status: 'delivered'` with `deliveredAt` timestamp.

7.6 Manual / On-Demand Callable Trigger (triggerScheduledNotifications)
------------------------------------------------------------------------
- Callable HTTPS function `triggerScheduledNotifications` allows manual invocation
  from admin portals or integration tests to force an immediate scan without waiting 5 minutes.

9. FIREBASE CLOUD FUNCTIONS PUSH DELIVERY ENGINE (FCM ADMIN SDK)
================================================================================

9.1 High-Priority Android Notification Channel
----------------------------------------------
- Channel ID: `cst_high_importance_channel`
- Sound: `default`
- Priority: `high`
- Visibility: `public`
- TTL: 86,400 seconds (24 hours)
- Guarantees heads-up banner display and audio alert even when the device is locked.

9.2 iOS APNs Background Wake-Up & Heads-Up Alerts
--------------------------------------------------
- APNs Headers: `"apns-priority": "10"`
- Payload APS:
  * `alert`: { title, body }
  * `sound`: "default"
  * `badge`: 1
  * `contentAvailable`: true (wakes background app for background data sync)

9.3 Cloud Function Recipient Resolution & Multicast Engine
-----------------------------------------------------------
- `processNotificationAndSendPush` resolves recipient tokens:
  1. Searches `/organisation/{orgId}/fcmTokens` filtered by `userType` and matching
     `forSupervisorName`, `forSupervisorId`, `forManagerName`, or `directUserId`.
  2. Falls back to root `/fcmTokens` if no scoped tokens are found.
  3. Suppresses self-notifications (matches `senderName` or `senderId`).
  4. Uses `admin.messaging().sendEachForMulticast(message)` for batch delivery.

9.4 Stale / Invalid FCM Token Pruning Mechanism
------------------------------------------------
- When FCM returns failure responses:
  * `messaging/invalid-registration-token`
  * `messaging/registration-token-not-registered`
- The Cloud Function automatically deletes the expired token document from Firestore,
  preventing wasted quota and stale multicast attempts.

9.5 Topic-Based Broadcast Fallback
-----------------------------------
- If direct device tokens are not registered or return zero targets:
  * Cloud Function automatically broadcasts to tenant topics:
    - `org_{orgId}`
    - `org_{orgId}_manager`
    - `org_{orgId}_supervisor`

10.1 2-Day Prior Expiry Detection Algorithm
--------------------------------------------
- Cloud Function Cron: `checkSubscriptionExpiryReminders`
- Trigger: Runs daily at 9:00 AM (Asia/Kolkata).
- Rules:
  1. Checks active subscriptions (`isSubscriptionActive === true`).
  2. Calculates remaining time: `0 < diffDays <= 2.05`.
  3. Duplicate suppression: Checks `lastExpiryReminderSentForEndDate` to prevent duplicate emails.
  4. Skips already expired or cancelled subscriptions.

13. VERIFICATION, RELIABILITY GUARANTEES & PRODUCTION BEST PRACTICES
================================================================================

1. Missing FCM Server Key:
   - If direct client HTTP push is unavailable, the system reliably falls back on the
     backend Cloud Function `onNotificationCreated` Firestore trigger.

2. App Running in Terminated / Killed State:
   - High-priority FCM payload with APNs `contentAvailable: true` and Android
     `channelId: cst_high_importance_channel` ensures notification delivers to the
     system notification tray even if the app process is terminated.

3. Background to Foreground Transitions:
   - `onMessageOpenedApp` catches taps from background state.
   - `getInitialMessage` with post-frame callback handles cold launches without crashing
     unmounted navigation contexts.

4. Multi-Tenant Cross-Contamination Protection:
   - Scoped queries strictly enforce `orgId == currentOrgId`.
   - Notification streams and batch read operations isolate data by organization.

5. Zero Duplicate Execution on Cron:
   - Firestore transactions ensure idempotent execution of scheduled notifications across
     multiple Cloud Functions container instances.

6. Self-Healing Token Lifecycle:
   - Stale or uninstalled app tokens returning `messaging/registration-token-not-registered`
     are immediately pruned from Firestore.
